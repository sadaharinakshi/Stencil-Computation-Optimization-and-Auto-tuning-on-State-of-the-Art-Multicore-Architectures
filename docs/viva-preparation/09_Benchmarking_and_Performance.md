# 09. Benchmarking Methodology and Performance Metrics

This document outlines the rigorous benchmarking methodology used in [bench/benchmark_3d.c](file:///c:/Users/Vaarshini Ravikumar/OneDrive/Desktop/Stencil-Computation-Optimization-and-Auto-tuning-on-State-of-the-Art-Multicore-Architectures/bench/benchmark_3d.c), defines all performance formulas, explains why initialization time is separated from compute time, and shows how to interpret the benchmark outputs.

---

## 1. Scientific Benchmarking Principles

Benchmarking parallel algorithms requires strict controls to eliminate measurement noise, operating system interference, and flawed metrics:

1. **Warmup Run:** Before measuring any kernel, a throwaway warmup run is executed. This primes CPU instruction caches, initializes OpenMP thread pools, and stabilizes CPU clock frequencies.
2. **Multiple Trials and Median Filtering:** Each configuration is executed over 10 independent trials. Instead of taking the arithmetic mean (which is vulnerable to OS background task spikes), we record the **median time** (or minimum time) to capture the true capability of the system.
3. **High-Resolution Timing:** Timers use `omp_get_wtime()`, which provides nanosecond-precision wall-clock timestamps via the hardware Time Stamp Counter (TSC).
4. **Identical Initial Conditions:** Across all 5 kernel configurations, the exact same deterministic temperature distribution formula $u(x, y, z) = \sin(idx \times 0.001)$ and grid dimensions are used.
5. **Separation of Initialization from Computation:** **CRITICAL REQUIREMENT.** Initialization (allocating and touching pages) must never be blended into the stencil compute loop timer. They measure two fundamentally different operations.

## 2. Core HPC Performance Metrics and Formulas

### A. GFLOP/s (Giga Floating-Point Operations per Second)
Measures raw arithmetic computational throughput:
$$\text{FLOPs per Grid Point} = 8 \text{ FLOP}$$
- 1 multiplication: $c_0 \cdot \text{center}$
- 5 additions: $\text{east} + \text{west} + \text{north} + \text{south} + \text{front} + \text{back}$
- 1 multiplication: $c_1 \cdot (\text{sum})$
- 1 addition: $(c_0 \cdot \text{center}) + (c_1 \cdot \text{sum})$

For a grid of size $nx \times ny \times nz$ evaluated over $T$ time steps:
$$\text{Total FLOPs} = 8 \times (nx - 2) \times (ny - 2) \times (nz - 2) \times T$$
$$\text{GFLOP/s} = \frac{\text{Total FLOPs}}{\text{Time (seconds)} \times 10^9}$$

### B. Speedup ($S$)
Speedup measures how much faster an optimized kernel executes compared to the serial reference baseline:
$$S = \frac{T_{\text{serial}}}{T_{\text{parallel}}}$$
- $S > 1.0$: Performance improvement.
- $S = P$ (where $P$ is thread count): Linear (ideal) speedup.
- $S < P$: Sub-linear speedup (typical in memory-bound applications).

### C. Self-Relative Parallel Efficiency ($E(P)$)
To measure how efficiently $P$ threads are utilized relative to a 1-thread parallel execution:
$$E(P) = \frac{T(1)}{P \times T(P)} \times 100\%$$
- At $P = 1$, $E(1) = \frac{T(1)}{1 \times T(1)} = 100.0\%$.
- A memory-bound code typically shows decreasing efficiency as $P$ increases because the shared memory bus bandwidth saturates.

## 3. Why Initialization Time Must Be Measured Separately

A major flaw in naive benchmarks is timing array allocation and initialization together with the stencil update loop.

### Why this is mathematically invalid:
1. **Different Operations:** Initialization is a memory-writing operation with zero floating-point arithmetic. Stencil computation is an arithmetic update involving 7 reads, 8 FLOPs, and 1 write.
2. **One-Time Cost vs. Amortized Cost:** In real scientific simulations, array initialization is performed **once** at time $t=0$, whereas the stencil update loop runs for **thousands of time steps** ($t = 1 \dots 10,000$). Mixing the one-time page fault cost into a 1-step benchmark creates a completely distorted representation of per-step computational throughput.
3. In our benchmarks, we measure:
   - `InitTime_ms`: Time taken by `serial_init_3d` or `first_touch_init_3d`.
   - `ComputeTime_ms`: Time taken strictly by the stencil update kernel.

## 4. Empirical Benchmark Results ($200 \times 200 \times 200$ Grid, 10 Steps)

The table below presents the verified results generated by `bench_3d.exe` on our test machine (Intel Core i5-12450HX, 12 threads):

| Configuration Variant | Init Time (ms) | Init Speedup | Compute Time (ms) | Achieved GFLOP/s | Compute Speedup |
|:---|:---:|:---:|:---:|:---:|:---:|
| **1. Serial Reference** | 460.0 ms | 1.00x | 9.50 ms | 6.54 GF/s | 1.00x |
| **2. Naive OpenMP** | 451.0 ms | 1.02x | 5.70 ms | 10.89 GF/s | 1.67x |
| **3. OpenMP + First Touch** | **62.0 ms** | **7.42x** | **5.20 ms** | **11.94 GF/s** | **1.83x** |
| **4. OpenMP + 3D Blocked** | 483.0 ms | 0.95x | 6.50 ms | 9.55 GF/s | 1.46x |
| **5. OpenMP + FT + 3D Blocked** | **53.0 ms** | **8.68x** | **6.30 ms** | **9.86 GF/s** | **1.51x** |

### Key Takeaways from the Data:
1. **First Touch Dominates Initialization:**
   Parallel First Touch slashes initialization time from **460 ms down to 53–62 ms** (an **$8.7\times$ speedup**). This is because page zeroing and OS page table allocation are parallelized across all cores.
2. **OpenMP Compute Acceleration:**
   Parallel OpenMP reduces stencil execution time from **9.50 ms to 5.20 ms** ($1.83\times$ speedup, 11.94 GFLOP/s).
3. **Bandwidth Ceiling:**
   Speedup tops out around $1.83\times$ because the 3D stencil is strictly bound by the ~32 GB/s physical DRAM bandwidth.
